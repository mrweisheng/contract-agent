# 合同生成前端改造 · 调研与方案对比

> 调研日期：2026-09-03  
> 调研对象：华星智能合同生成系统（contract-agent）前端  
> 落地形式：4 套高保真可交互原型（见 `prototypes/`）

---

## 一、现状诊断

### 1.1 业务事实
- 7 份合同模板（卖车、过户×2、粤 Z 新办×4 口岸）
- 表单字段 5~10 项/类型（部分含 subfield）
- 付款计划 2~3 期预设
- LLM 完成两件事：**字段抽取** + **付款约定解析**
- 实际**核心使用场景**：把客户的口头/微信描述粘进来 → AI 抽取 → 人工复核
- 表单的**真实价值**：兜底（AI 漏字段）+ 审核位（金额必对、币种必明、口岸必对）

### 1.2 现版痛点（基于 `app.js` + `style.css` 行为推断）
| 痛点 | 描述 | 证据 |
|---|---|---|
| **入口压迫感** | 进站默认就展开「合同信息」3 张档案卡 + 5~10 个 input + 1 个付款表 | `app.js:519`（`<div class="id-cards">`）、`app.js:576`（`<table class="pay-table">`） |
| **AI 价值被埋没** | 智能录入只是一行 textarea + 一个按钮，无引导 | `app.js:491-503`（`<div class="nl-compact">`） |
| **确认动作分散** | 缺失项要人眼对照 5 个 input + 1 个表 + 1 个币种 | `app.js:684-689`（底部 status pill 列表） |
| **场景无样板** | 4 个 placeholder 写了例子，但只能点一次看到 | `app.js:419-424`（`NL_PLACEHOLDERS`） |
| **生成结果淹没在卡片尾** | 用户要滚到付款表之后才看到「下载」按钮 | `app.js:649-678`（生成结果卡） |
| **历史与上下文隔离** | 历史抽屉独立按钮，与当前正在编的合同无关联 | `app.js:704-744` |
| **拟物过度** | 「档案卡」「印章」「水印」「宋体」装饰较重，对内部高频用户偏仪式化 | `app.js:521`（`:data-wm="g.title..."`） |
| **没有「反悔/重做」指引** | 一旦点了 AI 抽取，没法快速对比「原文 vs 提取结果」 | — |

### 1.3 真实用户的脑回路
1. 客户微信发了段话 → 复制
2. 打开系统 → **希望立刻就贴进去**
3. 看到「正在理解客户描述」的反馈
4. 看一眼哪些字段对上了、哪些没对上
5. 改/补没对上的 → 选币种 → 看一眼分期对不对 → 生成
6. 下载 → 关页面

> 整个过程里，"主动填表"只是**修边角**。当前界面却把"填表"摆成了主舞台。

## 二、行业调研结论

> 综合 LinkedIn (Holston 2024-25)、Smashing Magazine (2024)、reloadux、Nielsen Norman、camarc、tribble、destra 等来源。

### 2.1 共识：**Hybrid UX 是 2024-2026 企业 AI 录入的最佳模式**

**「对话起手 → 表单承接 → 确认收尾」三段式**（LinkedIn, Holston）：
- 对话擅长：发现低频入口 / 引导意图 / 复杂分支
- 表单擅长：已知字段的快速录入、批量校验、视觉总览
- 确认环节：在用户信任与提交效率之间架桥

引用：
> *"The agent opens the conversation… If structured input is required, a mini-form appears inline (3–5 fields). Once the mini-form is submitted, the agent summarizes the captured inputs and asks: 'Got it. Submit now or make edits?'"*

### 2.2 AI 抽取的「Review-and-Confirm」模式

camarc（合同 AI）研究指出：
- **AI 提取是起点，不是终点**。结构化数据在被下游使用前必须有人确认。
- **置信度可视化**是关键：低置信度字段高亮，提示"重点核"
- **审计轨迹**：AI 填了什么、人改了什么，必须可追溯

### 2.3 表单场景的 9 条原则（codetrait 综合）

1. **字段标签要短**——LLM 容易说废话
2. **避免把一个字段拆成多轮对话**——速度损失巨大
3. **可预测性**——同样输入，每次都应得到同样布局（不要 LLM 重排字段）
4. **进度可见**——总是告诉用户在第几步
5. **用户掌控**——可随时切换"打开完整表单 / 取消"
6. **识别优于回忆**——按钮、菜单、快速回复
7. **匹配任务模态**——已知字段走表单，意图型走对话
8. **清晰优于个性**——企业场景里简短胜过俏皮
9. **错误处理**——AI 误读时给个回退路径

### 2.4 合同类录入的共性

- 律所/法务 AI 工具（Ironclad、LinkSquares、tribble、camarc）都遵循**「文档视图 + 红色 diff」**模式
- 用户面对的不是表单，而是"已经填好 80% 的合同"，点哪里改哪里
- 这正契合你的项目——模板是固定的、字段是预设的、客户描述是兜底的

### 2.5 Baymard / 落地数据

- 14 个字段以上表单放弃率陡增
- 多步 + 进度条 + 必填项明示，能把完成率从 30% 提到 60%+
- **AI 自动填字段时**，"显示 AI 填了什么"比"AI 自动跳过字段"显著降低用户焦虑

## 三、改造方向（结论先行）

### 3.1 核心改造（任何方案都建议做）
1. **重构主流程叙事**：「粘文字 → 核对 → 生成」三幕，每幕有独立完成感
2. **AI 高亮改用「色块 + 角标」**，保留可识别性，弱化装饰
3. **缺项提示要就近**：不要在底部"X 项未填"，直接在字段旁边
4. **生成按钮常驻底部**，并把"还差什么"和按钮合并为单一信号
5. **示例话术变成"模板库"**：4 个业务类型 × 3 个常见度 = 12 条预设，可一键填入
6. **付款表做成可拖拽行 + 大字号数字**，不要藏在折叠里
7. **历史接入到合同流**：当前合同是历史里的某个状态，可重打开、续生成

### 3.2 不建议做的
- 引入 chat 取代表单（违反"已知字段走表单"原则）
- 用"对话式"标签把"AI 提取"按钮改名为"开始聊天"（用户更困惑）
- 砍掉"档案卡/印章"的视觉风格（用户对此已有认知，突然移除会失锚）——**保留为可选主题**
- 改成 SPA 路由多页（用户实际操作是单线流程，多页会增加导航成本）

## 四、四个方案对比

| 维度 | A · 对话优先 | B · 合同草稿视图 | C · Notion 流式 | D · 保守过渡 |
|---|---|---|---|---|
| **核心隐喻** | 跟 AI 同事聊天 | 直接看到合同 | 一页可滚动文档 | 现有架构的瘦身 |
| **AI 反馈位置** | 聊天流里 | 草稿文档里高亮 | 字段旁小气泡 | 顶部通知条 |
| **表单存在感** | 聊到一半弹出 Review Card | 隐藏在草稿里 | 占主舞台，干净 | 保留 3 张卡，间距加大 |
| **生成按钮** | 聊完最后一步出现 | 草稿定稿后右下浮动 | 单页底部固定 | 底部固定（现状） |
| **拟物/装饰** | 极少 | 强（红章/宋体） | 极少 | 保留（微调） |
| **改造成本** | 高（重写交互模型） | 高（重写视觉） | 中（重构 + 减项） | 低（CSS + 少量 JS） |
| **学习成本** | 中（要学对话节律） | 低（合同就在眼前） | 低（一眼到底） | 极低（不变） |
| **适用人群** | 新人 / 不熟字段 | 业务老手 | 所有人 | 极保守的老用户 |
| **风险** | 对话节律失真会很别扭 | 视觉改动大，老用户不适 | 流式滚动长时可能累 | 解决不了根本问题 |

### 推荐组合
- **首推 B（合同草稿视图）**——最贴合业务语义（合同生成系统），最容易让用户"看到自己在做什么"，且 AI 抽取的视觉化展示最自然。
- **备选 C（Notion 流式）**——如果不想动现有视觉语言、走最稳路线。
- **A 不建议作为主方案**——对话式会让你失去表单的结构化优势。
- **D 作为新视觉语言上线前的过渡**。

## 五、交互细节设计要点

### 5.1 输入区的演进
- textarea 默认 1 行高度，**聚焦自动撑到 6~8 行**
- 旁置**「示例」下拉**（4 类业务 × 1~3 模板），点一下预填
- 提交后变进度条：理解→抽取→解析付款→校对，**2~3 阶段，每个 1 行文字**

### 5.2 字段审核的视觉
- AI 填的字段：底色 `#FFF5E0`（极淡琥珀）+ 右上角小「AI」角标
- 必填已填：左侧 3px 绿色描边
- 必填未填：左侧 3px 红色描边 + 内嵌 placeholder
- 用户改过：AI 角标消失，改为"已核对 ✓"小标签

### 5.3 付款表的演进
- 从「行式表格」改为「**大卡片堆叠**」：每期一张卡
- 卡片里金额字号 32px+，让用户一眼看金额
- "合计 = 总费用" 用一条粗横线 + 状态徽章（绿 ✓ / 橙 差额 / 红 缺期）

### 5.4 生成按钮的信号
- 默认态：实心主色 + 「生成合同」
- 缺项态：同位置 + 橙色 + 「还差 X 项，禁用」+ tooltip 列出具体项
- 进行态：进度条 + 阶段名
- 成功态：保持位置 + 变绿色 + 「下载 ↓」

### 5.5 历史接入
- 顶部右上角小圆点：显示今日已生成数
- 点开：右侧抽屉（不是模态），可搜编号/客户
- 当前合同如果和历史某条同编号/同客户，自动提示"可能与 0828-001 是同一单"
