# 结算单铁律速查（制单前默念，逐条照做）

本文件与 `SKILL.md`、`rules.md` 完全一致，只是把散落的铁律集中到一页，便于快速核对。**不得改写、不得删减。**

## 一、汇率与折算

1. **人民币折港币一律 ×1.01（2026-10-02 强调，最高优先级铁律）。** 任何人民币→港币的折算（包括用双币等值比率折算时）都必须再乘 1.01，**不得以「等值已含 ×1.01」为由跳过**；只有用户直接给出最终港币应收金额、或当次明确说不用乘时才例外。`rate.apply_101` 默认 `true`。例：¥150,000 × 1.16938 × 1.01 = $177,161.07。
2. **×1.01 只做不说（2026-10-02 指定）：单据上的任何文字——备注、金额说明、警告——都不得出现「×1.01」「收款系數」等字样**，客户不需要知道。内部照算，纸面不提；自定义 `note` 时同样遵守。
3. **取实时汇率时，口径必须是「百度实时汇率」，不得用中国外汇交易中心中间价代替（2026-10-09 当场纠正，铁律）。**
   - 标准口径就是百度搜索结果卡（FinScope 数据）显示的一行：`1 人民币 ≈ 1.1726 港币 / 1 港币 ≈ 0.8528 人民币`。
   - 两者相差约 0.5%–0.7%：2026-10-09 中间价 `0.85798` vs 百度实时 `0.8528`，在 ¥160,000 量级上港币口径差 1,100 元以上，**足以改变客户实收金额**。
   - 实操：**优先请用户直接把百度截图上的数字发过来**；自己取数时抓百度「人民币港币汇率」结果卡，**不要抓中国货币网 / 银行间外汇市场中间价**。
   - 传入 `rate` 时 `source` 写「百度实时汇率」，`basis` 写 `today`。
4. **汇率是「分部分」套用的，不是一刀切（淇淇 2026-10-10 澄清，铁律，最高优先级）。**

   | 部分 | 用哪套汇率 |
   |---|---|
   | ① 合同内款项：总价 / 定金 / 第二期款 / 尾款 | **淇淇明确给出的等值金额，原样取用**；**她没给就直接用制作当天的百度实时汇率** |
   | ② 合同外杂费 / 政府收费 / 客户垫付 | **制作当天的百度实时汇率**（人民币→港币再 ×1.01） |
   | ③ 既无合同、又没给等值，只有一个总金额 | 全部按当天百度实时汇率算 |

   - **判据只有一条：这一笔淇淇给过等值金额吗？给过就用她的数；没给过就按当天百度实时汇率。**
   - **严禁自行从合同总价的双币对推算尾款等值**（合同只给总价、没给尾款等值 → 尾款走当天汇率）。
   - 淇淇给了双币等值（如尾款 ¥178,000 / $210,044）＝合同白纸黑字写明的，**禁止再按当天汇率重折**（许兰坛教训：重折算出 $205,765，与合同的 $210,044 差 721 港币）。
   - **港币项不再被折算**：杂费里本身就是港币的金额原样进港币口径，不要再折成人民币又折回来（会多乘一次 1.01）。
   - 两个付款口径（合同内、合同外）本就用不同汇率，**不要求互相验算**，别拿一方去反推另一方。

5. **汇率精度取 5 位小数，不能只用百度显示的四位（2026-10-10 纠正）。**
   - 百度显示 `1 人民币 ≈ 1.1726 港币`，实际换算用的是 `1.17263`；用四位会让 ¥186,631 少算 5 港币，客户验算对不上。
   - 取数优先级：① 用户百度截图上的换算结果反推精确汇率（最准）→ ② 实时汇率插件给的完整小数（如 1.17262485，取 `1.17263`）→ ③ 百度显示值只在实在拿不到时用，并在交付时说明。
   - 写入 `rate.cny_to_hkd` 时保留 5 位小数。

6. 用户规定按合同汇率时一律按合同汇率（`basis: contract`、`date` 写合同签订日），不得用实时汇率覆盖；合同没有汇率或双币等值金额时**先追问**，不默认使用操作日实时汇率。

7. **严禁混币种直接相减（2026-10-10 严厉纠正，最高优先级铁律）。** 不同币种的钱**不能直接加减**。
   - 客户垫付的是港币现金、要抵扣的是人民币尾款，必须**先把港币按百度实时汇率折成人民币**再减，反之亦然。
   - 反面教材（许兰坛 v5）：`¥178,000 − $5,000 = ¥173,000` 直接把 5,000 港币当 5,000 人民币减，**凭空少收 736 元**。淇淇原话：「178000 的人民币减去 5000 港币，为什么能得出 173000 的人民币呢？这个错误太严重了。」
   - 正确算法（现行）：港币折人民币 `$5,000 × 0.852785 = ¥4,263.93` → 人民币口径 `¥178,000 − ¥4,263.93 = ¥173,736.07` 截尾为 **¥173,736.00**；港币口径 `$210,044 − $5,000 = $205,044.00`。
   - **同一币种内部才可以直接减**（港币口径里减港币、人民币口径里减人民币），跨币种一律先折。
   - `extra_paid[].face_offset = true` 这个「面值直减」开关**已永久禁用**，任何情况下都不要再打开。

## 二、金额显示

8. **「您今日需付」金额一律截尾到元，小数固定显示 `.00`（2026-10-02 指定，铁律）。** 无论计算结果小数是多少（如 $177,161.07），横幅上都只显示 $177,161.00；**不是四舍五入，是直接把小数位舍成 0**。明细行与备注不受此限，仍按实际两位小数书写。
9. 明细金额一律保留两位小数，负数表示已付款或扣减。

## 三、双币列示

10. **用户给的是人民币金额，就按人民币列示**（两地牌常态）。人民币区行显示 `¥`，不得擅自把折算后的港币值当成主金额。
11. **未收款项只在原币种明细里列示一次**，港币等值只进「备注」和「您今日需付」的另一个口径。绝不把同一笔款项再开一行港币明细。
12. **已收款项填客户实付金额，不是折算出来的理论金额**（例：客户实付 `$58,400`，合同等值 `$58,469`，则明细行写 `-$58,400.00`，差额在备注注明）。核算仍按合同等值（`$58,469`）推第二期款与尾款。
13. **涉及两种币种时，「您今日需付」并列两个付款口径**（折合人民币 + 折合港币），不是只给一个。
14. 备注写双币等值对、汇率口径；`rules.md` 要求注明「匯率核算以合同簽訂日為標準」。
15. **「您今日需付」的两个币种金额之间必须画 `/` 分隔（2026-10-09 强调，铁律）。** 只要横幅并列显示人民币和港币两个付款口径，两个金额之间就**必须**有一个 `/`，**不得留空白、不得只靠间距区分**。只有单一币种时不需要斜杠。
16. **等值金额之间一律用斜杠 `/` 分隔**（`¥160,000.00 / $188,360.96`），两个货币符号中间不留空格替代。
17. **本次应收的合同内款项，必须在备注栏给出它的人民币／港币等值换算金额（2026-10-09 指定，铁律）。**
    - 指的是**明细表最后一行、本次要收的那一笔合同内款项**（如「車牌尾款」），**不是**含合同外杂费的「您今日需付」总额。
    - 写法：`車牌尾款為 ¥160,000.00 / $188,360.96。`
    - 港币等值必须与单据口径自洽：**备注里的港币等值 + 港币杂费 = 「您今日需付」的港币数**。
    - 用户已直接给出等值金额（`hkd_equiv` / `cny_equiv`）时，用用户给的数，不重复折算。

## 四、收款范围

18. **本次收哪几笔由「结算类型」决定。** 结算类型写「收第二期款」就只收第二期款，**不能自动把尾款算进去**，车牌尾款一类未收款按「下次收款」列示（浅灰蓝、不计入今日需付），**不得自行合并结算**；结算类型写「收尾款」就只收尾款。判断不了或用户标注与结算类型矛盾时，**先问用户本次收哪几笔**，不要猜。

## 五、以客户实付为准

19. **客户实付金额和合同等值金额分开记录，一定以客户的实付金额为准**（录入明细时写实付，合同等值只在备注与核算口径里体现）。

## 六、赠送项

20. 状态下拉里的「赠送」＝**金额照填、照显示，只是不进合计**，不是把金额清零。
    - 项目名后加「（贈送）」（繁体），应收金额列写具体金额，金额分位栏照填各位数字。
    - 赠送项**不进「您今日需付」**，也不进任何币种的应收合计。
    - 合同内已收／未收款项标赠送时，目前仍按金额 0 处理；如需照价显示，先与用户确认再改。

## 七、交付与检查

21. **PDF 与 PNG 同一次生成、同时交付**（`--png` 一次出齐，PNG 优先展示），**先出 PDF、确认后再出 PNG 的慢流程已被明确否定**。PNG 自动进剪贴板，⌘V 可直接发微信。
22. **每单做完必须「检查」这个动作，不能跳过（2026-10-10 第二次强调）。** 交付前逐条过一遍：
    - [ ] 合同内部分是否等于淇淇给的等值／当日汇率折算值？
    - [ ] 明细逐项加总 = 横幅「您今日需付」，两个币种都要对得上；
    - [ ] 备注里的尾款双币等值 = 明细最后一行那一笔，且币种符号间有 `/`；
    - [ ] 赠送项：项目名带「（贈送）」、金额照显示、不进任何合计；
    - [ ] 单据纸面**不出现**「×1.01」「收款系數」等内部口径字样；
    - [ ] 有 warnings（溢出／对账不一致／多收）必须先查明再交付；
    - [ ] 参照《铁律速查》再扫一遍。**检查要有结论说给用户听，不能静默通过。**
23. **有金额冲突必须先问，不得猜测**：金额缺币种、总价与已收对不上、杂费实收只有一个总数但涉及多币种、合同汇率与用户要求冲突、同一项目两个金额、业务同时符合多个模板——都要先反馈追问。
24. **本项目只处理收款结算单**，不处理飞书表格、催款或会计凭证。
25. **存底 JSON 的内部备忘要用下划线私有键**（`_memo` / `_selfcheck` / `_due_today`）。顶层 `note` 会被引擎当成单据备注**印到客户单据上**，把含「×1.01」的内部说明放这里等于违规露底。

## 八、版式

26. 一切以 `assets/收款结算单统一版式基准.pdf` 为唯一视觉母版，不得另行设计、改色、缩小字号或恢复旧版式；`SKILL.md`「视觉定稿参数」一节为最终版，照做即可，不要再问。
27. 顶部信息栏字段过长时**折行，绝不缩字号**（`S_META = 13.1` 恒定）。
28. 除「群名」字段内容和「大陆收款账户」整块用简体中文外，其余中文一律香港繁体。

## 九、一次性收全款（客户此前一分未付）

29. **结算类型写「收尾款」但客户从未付过款时，总价＝本次应收，不要再造一个「车辆尾款/车牌尾款」行。** 已实测引擎行为（`settlement_compute.build_spec`）：

    | 传法 | 明细行 | 今日需付 |
    |---|---|---|
    | `contract_total` 12000 HKD + `contract_unpaid` **[车辆尾款 12000 today]** | 車輛總價 / 車輛尾款 / 過戶 三行 | $13,500.00 ✅ 但出现「尾款」字样 |
    | `contract_total` 12000 HKD + `contract_unpaid` **[]**（留空） | 車輛總價 / 過戶 两行 | $13,500.00 ✅ **推荐** |
    | `contract_unpaid` 里放 **[车辆总价 12000 today]** | — | ❌ $1,500.00，总价泄漏到今日需付之外 |

    - **关键：item 名里含「总价」的 `contract_unpaid` 行会被引擎跳过**，不要用它来代表本次应收。
    - `contract_total` 本身已计入今日需付，所以「总价 + 杂费」＝一次性全款的正确总金额。
    - 判断要不要改写法，只需问一句：「客户此前有没有付过定金／任何已收款？」没有 → 走第 2 行写法。
    - 纯港币单在这一写法下 `note` 为 `null`，`amount_note` 自动变成「本單全部款項均為港幣，無需進行跨幣種換算。」不需要强行补人民币等值。
